# Handrail

Built for the PayPal "Build What's Next with PayPal and AI" hackathon on Devpost.
Deadline: Nov 12, 2026, 12:00 pm PT. Target: Nov 10, 2026.

## What Handrail is

A safety layer between an AI agent and PayPal's Agent Toolkit / sandbox MCP server. To the agent it looks like PayPal's MCP server, exposing the same tools, but it checks every money-moving call before forwarding it.

## Positioning

- Handrail answers "should my agent be allowed to make this PayPal call?", not "did the work earn payment?"
- It protects a business from its own agent, sitting in front of PayPal's Agent Toolkit / MCP server.
- Core pitch: drop-in (an existing Agent Toolkit agent works with no code changes; Handrail never claims to be PayPal). Point an existing Agent Toolkit agent at Handrail and every money-moving call gets limits, approval, idempotency and an audit trail, with no agent code changes.
- Lead with refunds (`create_refund`) and dispute concessions (`accept_dispute_claim`) in docs and the demo. Capture (`pay_order`) is secondary.
- Another entry, Stood (github.com/ma-za-kpe/stood), is a proof gate for agent-to-agent milestone payments. It shares some philosophy (rules move money, models only report), idempotent hold/capture/void, and AG Grid. Don't copy its wording or framing in the README, UI text or docs.

## The problem

An agent connected to PayPal's toolkit can issue refunds, concede disputes, cancel invoices or subscriptions, and capture payments with nothing checking the call first. The toolkit only lets you turn tools on or off. It has no approval step, no spending limit, and no per-call idempotency key (PayPal-Request-Id is set per client, never per call), so a retried request can duplicate an action. There's also no record of what the agent actually did.

Evidence: github.com/paypal/agent-toolkit issues #82, #95, #98.

Money-out tools to guard: `create_refund`, `accept_dispute_claim`, `cancel_sent_invoice`, `cancel_subscription`, `pay_order` (capture), plus invoice sending.

## Components

- **Policy engine**: deterministic rules decide allow / needs approval / block for each call (amount ceilings, per-tool rules, rate limits, payee checks). AI never makes this decision.
- **Approval queue**: held calls wait for a human to approve or reject, then forward or return a structured denial.
- **Idempotency manager**: assigns a stable PayPal-Request-Id per logical operation so retries never duplicate.
- **Audit log**: SQLite, tamper-evident (hash chain), recording request, decision, reason, and PayPal response.
- **Webhook endpoint**: receives PayPal events (refund completed, invoice paid, dispute updated), matches them to the original agent request, and flags mismatches.
- **REST API for the dashboard**: audit log, policies, pending approvals, people, invites, agent keys. Roles enforced server-side on every route.
- **React dashboard**: public homepage at `/`, sign-in/sign-up, and the dashboard at `/app`: plain-English policy editor (AI compiles English into structured rules; the user confirms), approval queue with live updates, audit log grid using AG Grid, team and agent-key management.
- **Users and agent keys**: admin / approver / viewer accounts; agents authenticate to `/mcp` with keys admins create.
- **AI usage**: compiling plain-English rules into structured policy and explaining flagged decisions. Enforcement is always deterministic code.

## Stack

TypeScript, Node.js, the official MCP TypeScript SDK (Handrail is an MCP server toward the agent and an MCP client toward PayPal), SQLite, React, and AG Grid. Hosted on Render. One repo.

## Verified facts (Oct 2026)

- PayPal's sandbox MCP server only works over **SSE** at `https://mcp.sandbox.paypal.com/sse` (46 tools). The documented Streamable HTTP path `/http`, and `/mcp`, return 404 even with a valid token. `npm run probe` re-checks this.
- The bearer token for the MCP server is a normal REST access token from `/v1/oauth2/token` (client credentials).
- SQLite uses Node's built-in `node:sqlite` (Node >= 22.13). `better-sqlite3` segfaulted on Node 23.4. Scripts pass `--disable-warning=ExperimentalWarning`.
- PayPal's MCP server reports API failures as a normal result (`isError: false`) whose text is JSON like `{"ok":false,"status":404,...}`. `isUpstreamError` in `src/gate.ts` treats those as errors.
- Many money tools carry no amount (full refunds, `pay_order`, `accept_dispute_claim`, `send_invoice`), so `src/policy/facts.ts` looks the amount up via read-only REST before deciding. Unknown amount or payee fails closed to `require_approval`.
- Idempotency (`src/idempotency.ts`): every non-read call maps to an operation (agent's `idempotency_key`, or a hash of tool + canonical args within a 1-hour window). Repeats of in-flight / succeeded / held / rejected operations are answered without contacting PayPal. The Agent Toolkit sets `PayPal-Request-Id` once per client (agent-toolkit `typescript/src/shared/client.ts`), so `create_refund`, `pay_order` and `accept_dispute_claim` are sent directly to the REST API (`src/paypal/direct.ts`, `DIRECT_TOOLS`) with a per-operation request id; the body and result format match the toolkit. Unknown outcomes (timeout, 5xx, crash) reuse the request id for direct tools and are held for approval for MCP tools. The call log's `request_id` holds the PayPal-Request-Id Handrail sent (direct tools at `begin`, REST fallbacks at `finish`); MCP calls have none (the toolkit's per-client id isn't visible); duplicates copy the original call's id (shown as "Original request ID" in the Activity drawer).
- PayPal's sandbox MCP server (Oct 28, 2026) answers every tool with `PAYPAL_API_SETUP_ERROR` "Unsupported cache mode: default" (paypal/AI-Toolkit issue #34; a bare MCP client gets the same, REST with the same token works). The toolkit raises that code when building the request, before sending, so the gate records it as `failed` and answers `REST_READ_TOOLS` (list/get disputes, list/show products, list/get invoices) from REST with the toolkit's URLs (`PayPalDirect.read`), and sends `REST_WRITE_FALLBACK_TOOLS` (send_invoice, cancel_sent_invoice, cancel_subscription) via `PayPalDirect.call` with the operation's PayPal-Request-Id (tests in `test/direct.test.ts`, `test/gate.test.ts`); other MCP tools return PayPal's error. These fallbacks send no `Prefer` header, like the toolkit (so a cancel answers 204 → `{success, invoice_id}`); send_invoice and cancel_sent_invoice verified live Oct 30, cancel_subscription only in tests. PayPal confirmed the regression on Oct 29; every call still tries MCP first, so the fallback stops on its own once fixed. README "Known PayPal issues". `npm run smoke` exits 1 on a `{"ok":false}` result.
- Webhooks (`src/webhooks.ts`, `src/webhook-endpoint.ts`): `POST /webhooks/paypal` verifies via `/v1/notifications/verify-webhook-signature`, stores each event once, and matches it to the forwarded agent call. Statuses: matched, mismatch (amount differs, or Handrail recorded failed/unknown), outside_handrail (refund or invoice cancellation with no agent call), unrelated, ignored. A refund event matches the call whose response has that refund id; the capture only stands in for calls with no refund id on record, so a different refund on the same capture is outside_handrail. `GET /api/webhooks` (`limit` ≤ 500, `since`), `/api/webhooks/counts` (per status), `/api/webhooks/:id` (with the payload, redacted).
- Verified end to end against the sandbox (Oct 10, 2026): a real capture via `pay_order`, then a 10-call retry storm on it gave one $5 refund at PayPal. Both webhooks (`PAYMENT.CAPTURE.COMPLETED`, `PAYMENT.CAPTURE.REFUNDED`) arrived signed, verified, and matched their calls. The registered webhook URL must end in `/webhooks/paypal`. PayPal can resend past events via `POST /v1/notifications/webhooks-events/{id}/resend`.
- Audit log (`src/audit-chain.ts`): every write to tool_calls, approvals and webhook_events appends an `audit_chain` entry in the same `BEGIN IMMEDIATE` transaction. `hash = sha256(prev_hash, seq, at, kind, ref, data_json)`; triggers reject UPDATE/DELETE. `verify()` recomputes the chain and replays it against the working tables, so edits to either are caught. The first entry (`chain.started`, written at boot) snapshots rows that predate the chain. `GET /api/audit` (`limit`, `ref`, `since`, `before` seq), `/api/audit/first`, `GET /api/audit/verify`; `GET /api/calls` also takes `since` and `before` (id). Truncating the newest entries is only detectable against a head hash noted elsewhere.
- Auth (`src/auth/`, `src/admin-api.ts`, `test/auth.test.ts`):
  - Accounts: Argon2id via `@node-rs/argon2` (prebuilt binaries; fine on Node 23.4). Sessions are random 256-bit tokens in an httpOnly, SameSite=Strict cookie (`handrail_session`), stored as SHA-256 in `sessions`, 7 days. `Secure` unless plain HTTP on localhost (`HANDRAIL_COOKIE_SECURE`).
  - CSRF: synchronizer token per session, sent as `X-CSRF-Token` on every cookie-authenticated change; any state-changing `/api` request whose Origin/Referer host differs from Host is refused (covers login CSRF too).
  - Login limits (in memory): 5 failures per IP+email and 30 per IP per 15 min; unknown emails still run an Argon2 verify.
  - Roles: admin > approver > viewer, checked per route in `createAdminApi`. The first non-demo sign-up becomes admin inside a `BEGIN IMMEDIATE` transaction (with `HANDRAIL_SETUP_TOKEN` set, only if the request carries it, checked in that transaction; `checkSetupToken` stops startup on Render without it; `GET /api/auth/session` says `setupTokenRequired`); later sign-ups need an invite (one use, one email, 7 days, stored hashed). An admin can't change their own role, and the last active admin can't be demoted or disabled.
  - `HANDRAIL_ADMIN_TOKEN`: local scripts only. Unset means every bearer token is refused on `/api`. `checkAdminToken` (src/auth/http.ts) stops startup if it's set on Render (`RENDER` / `RENDER_SERVICE_ID`). Acts as admin and is always recorded under `ADMIN_SCRIPT` ("Admin script", id `admin-script`), with an optional script label: "Admin script (<by>)".
  - Approvals record `decided_by` (name) and `decided_by_id`; policy changes record `byId`. User, invite and agent-key changes are audit-chain entries (never password hashes or key material).
  - Agent keys (`hr_agent_…`): shown once, stored as SHA-256, revocable. `/mcp` (`src/mcp-endpoint.ts`) refuses calls without a valid key (or `HANDRAIL_AGENT_TOKEN`); every call, duplicate and approval records the agent (`agent_key_id`, `agent_name`), and stdio calls are recorded as "Local agent (stdio)".
  - Demo: `HANDRAIL_DEMO_ACCESS=true` seeds "Demo Approver" (approver, random unusable password) and enables `POST /api/auth/demo`. It can't sign in with a password, change its profile or password, or become admin.
- Secrets (`src/redact.ts`, `src/error-boundary.ts`, `test/redact.test.ts`):
  - `loadConfig` registers the PayPal client id/secret (and their Basic encoding), admin and agent tokens and the Anthropic key; the token manager registers each PayPal access token. `redact()` removes registered values plus credential shapes (Bearer/Basic, `sk-…`, `A21AA…`, `hr_agent_…`, `access_token=`/`password:` pairs).
  - Applied in `log()`, at the gate's entry (agent arguments, so nothing secret is stored, audited, shown to approvers or the AI, or forwarded) and on every PayPal result, in `AnthropicLlm.json` (prompts), in admin API error messages, and in demo run errors.
  - Unexpected errors: the admin API and the top-level HTTP handler return a generic 500 with an `errorId`; the redacted detail is logged. No stack traces reach clients.
  - Prevention: `scripts/check-secrets.mjs` (no dependencies; patterns, forbidden paths like `.env`/`*.db`/`*.pem`, and the exact values in the local `.env`, never printed) runs from `.githooks/pre-commit` (`npm install` sets `core.hooksPath`; gitleaks runs too if installed) and in `.github/workflows/secrets.yml` with gitleaks over the full history, plus `npm test`. Test fakes are built at runtime (string concatenation) so they don't trip the scanner; a deliberate fake line can end with `secret-scan: allow`.
  - Audited Oct 13, 2026: no secret in any commit (exact `.env` values and gitleaks), none in the browser bundle.
- Alerts (`src/notify/`, tests in `test/notify.test.ts` and `test/auth.test.ts`):
  - After a call is held, the workspace's `onHeld` writes the AI brief, then (when it's ready or after `alertWaitMs`, 20 s) calls the notifier with the approval. The alert says what the agent wants (tool, amount), the customer (payee email, else the PayPal id it targets; ids not matching `[A-Za-z0-9-]{1,40}` are "(not shown)"), the rule that held it, the AI summary's first sentence (links stripped) and `<HANDRAIL_PUBLIC_URL>/app#approvals/<id>`. No approve links, tokens or agent-written text (notes, reasons).
  - `LiveNotifier`: email via Brevo (`BrevoEmail`, one request per recipient: active approvers/admins with `email_alerts` on, never viewers or the demo account) and Slack (`postToSlack`, only `https://hooks.slack.com/(services|workflows|triggers)/…`). Off without `BREVO_API_KEY`+`HANDRAIL_ALERT_FROM` and without a Slack webhook. Calls already decided are skipped. Every alert is an `alerts` row and an `alert.sent` audit entry (names, never addresses); failures are logged, never thrown.
  - `PreviewNotifier` (demo workspaces): records the message as a preview, sends nothing.
  - `SettingsStore` (real DB, `settings` table): the Slack webhook, admin-only (`GET/PUT /api/settings/alerts`, `POST /api/settings/alerts/test`), returned only masked (`hooks.slack.com/…/abcd`), audited as `settings.changed` without the URL, registered for redaction. Users toggle their own email with `PATCH /api/me/alerts`.
  - Dashboard: header chip (Alerts off / on: email + Slack / preview only), alert line or demo preview on each approval card, `#approvals/<id>` focuses that approval (or says what happened to it), and `/login?next=` returns there after sign-in.
- Held-call expiry: `approvals.expireAfterHours` in the policy (default 24, max 720; `holdTtlMs`). Expired approvals are never sent; the held call's call-log row gets outcome `expired`, `approval.expired` is in the audit chain, and the agent gets `status: "expired"`. Editable in the Policy tab. - Verified facts (`src/policy/facts.ts`, `VerifiedFacts` in `src/policy/types.ts`): `resolveFacts` looks up what PayPal says before deciding: `create_refund` → the capture, then its order (`supplementary_data.related_ids.order_id` or the `up` link) for the payer (PayPal account, or `payment_source.card` name and last digits) and refunds (order `purchase_units[].payments.refunds`, COMPLETED or PENDING, per capture via each refund's `up` link); `pay_order` → order and payer; `accept_dispute_claim` → status, reason, stage, amount, `seller_response_due_date`, buyer; invoices; `cancel_subscription`. - Cumulative limits (`cumulative_limit` rule, `checkCumulative` in `src/policy/engine.ts`, tests in `test/cumulative.test.ts`): create_refund only; `per` capture | order | payer | agent; `windowSeconds` only for payer/agent (agent defaults to a day). Capture falls back to the log if PayPal fails; order/payer need PayPal to identify them, so they fail closed (card payments have no payer id). Default policy: `refund-capture-total-over-100`, `refund-agent-daily-300`.

- Default port is 8787 (3000 is used by another app on the dev machine).

## Commands

- `npm run build:web`: builds the dashboard (`web/`, React + AG Grid) into `web/dist`, which Handrail serves (homepage at `/`, dashboard at `/app`; the first sign-up becomes admin). `npm run dev:web` runs it with hot reload on :5173, proxying `/api` to :8787.
- `npm test`: unit tests (policy engine and gate; no network).
- `npm run smoke`: starts Handrail over stdio, lists tools, makes one read-only call.
- `npm run demo:approval [-- --auto]`: end-to-end allow / hold+approve / block / hold+reject against the sandbox, using a fake capture ID so no money moves.
- `npm run sandbox:capture [-- --amount 20.00]`: creates a real sandbox order, waits for buyer approval in the browser, captures it through Handrail, prints the capture ID.
- `npm run demo:retry-storm [-- --capture <id> --amount 5.00 --count 10]`: identical refunds fired at once; PayPal receives one.
- `npm run approvals [-- approve|reject <id> [note]]`: decide held calls via the admin API (uses `HANDRAIL_ADMIN_TOKEN`; local only, recorded as "Admin script").
- `npm run audit:verify`: checks the hash chain and that the working tables match it; exits 1 on tampering.
- `npm run probe`: re-checks which PayPal MCP endpoints work.
- `npm run real-model-run [-- python|ai-sdk|langchain-js]`: runs the switched examples with a real LLM (OPENAI_API_KEY in .env) against a throwaway Handrail (port 8795, temp DB, random agent key/admin token, no AI briefs or alerts) and fresh 200.00 USD sandbox sales; examples get a minimal env (no PayPal credentials). Report in real-model-runs/ (ignored): agent's final words and, from Handrail's call log, whether the held $150 refund was retried.
- `npm run check:secrets`: scans every tracked file for secrets (the pre-commit hook checks staged changes).
- `npm run check:drop-in [-- --update]`: compares what an agent sees from PayPal's MCP server with what it sees from Handrail; exits 1 on any difference beyond the documented additions.

## Auth

Handrail holds `PAYPAL_CLIENT_ID` and `PAYPAL_CLIENT_SECRET` and gets access tokens itself via the OAuth client-credentials flow, refreshing before expiry (tokens last roughly 9 hours). The agent never sees PayPal credentials. Secrets stay in `.env`, server side only.

## Build order

1. Proxy that passes MCP calls through to PayPal's sandbox MCP server and logs them. Drop-in: same server identity, tools and schemas as upstream.
2. Policy engine and approval flow, with `create_refund` and `accept_dispute_claim` first (rules, approval, demo coverage); other money tools after.
3. Idempotency and webhook matching.
4. Dashboard. The AG Grid audit log and the approval queue are the most polished parts: filtering, status badges, and row detail showing the decision reason and PayPal's response.
5. Plain-English policy feature, demo polish, README, demo video.

## Demo (under 3 minutes)

An over-limit refund gets held, the approval card shows an AI explanation, a human approves, and the log records it. Then a retry storm produces no duplicate. Then a plain-English rule compiles to policy.
